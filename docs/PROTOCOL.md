# Local transfer protocol, version 1

Normal transfers use TLS 1.2. Each receiver/sender host has a self-signed RSA certificate. Its SHA256 fingerprint is carried in the QR; the Android client validates that exact identity before sending the pairing secret or file details. Windows keeps its identity encrypted for the current Windows user using DPAPI. Android uses AndroidKeyStore; Android servers offer ECDHE-RSA suites to match their signing-only key. Pairing secrets are random 256-bit values and expire after ten minutes. Hosts accept private/loopback/link-local IPv4 peers and require batch approval. QR contents include sensitive pairing/hotspot details; they are not uploaded or added to transfer history.

The QR is `shareme-rowell://pair/<base64url-json>`. JSON fields: `v=1`, `hosts` (private IPv4 strings), `port`, `fp` (64 lower-case hex characters), `code`, `mode` (`send`/`receive`), `name`. App-created hotspots add `ssid` and `password`.

Share Mode 1.0.3 retains this scheme/version for compatibility. Android advertises LAN interfaces instead of cellular/VPN addresses. App-created hotspot codes include only the hotspot endpoints. The joining client requests the named SSID even when another Wi-Fi uses the same subnet, waits for IPv4 link properties and uses that Network's socket factory. TCP connection and TLS negotiation have separate bounded timeouts before approval/transfer waits. Idle listener codes refresh when local addresses change.

Version 1.0.4 uses the `shareme-tls-v2` AndroidKeyStore alias, authorizing the raw RSA signing operation used internally by Conscrypt. A server-only key-manager wrapper selects only this alias for both socket and engine handshakes, so the old incompatible alias cannot be chosen after an upgrade. TLS remains restricted to 1.2/ECDHE-RSA and the QR still pins the exact certificate. The application installation certificate and QR wire protocol are unchanged.

The Android 1.1.0 development candidate adds optional DNS-SD discovery (`_sharemode._tcp.`). TXT fields are `v=1`, a random app `id`, a bounded chosen `name`, an avatar encoded as five bounded integers, and `fp`. The platform resolves the private IPv4 host and dynamic listener port. This public advertisement contains no pairing secret, Wi-Fi credentials, or file metadata. Searching is restricted to the visible Send screen with a selection; advertising and nearby requests require an open, visible, idle Receive screen. No IP-range scan or continuous background discovery is used.

A nearby client first sends `{v:1, op:"nearby", name, avatar, nonce}` over TLS, with no QR secret or selected-file details. The nonce is a fresh random 128-bit value encoded as 32 lowercase hex characters. This path is accepted only by an unexpired, visible receive host and cannot pull from a send host. Both devices derive a 64-bit comparison code from SHA256 of `ShareMode-nearby-v1:<actual-server-certificate-fingerprint>:<client-nonce>`, displayed in four groups. The client pins the full discovered certificate during TLS, but public discovery alone does not authenticate it: the sender must compare the connection-specific code against the receiver's transfer banner before sending any filenames. Binding both the certificate and fresh nonce prevents another client from reusing a receiver's static displayed identity code.

The host reserves the same TLS channel, displays its derived code and acknowledges `{ok:true,stage:"nearby"}`. The sender confirms a matching code and its selected files, then sends the ordinary push offer on this same channel. The receiver sees the offered files and must compare/confirm the same code before approving payload transfer. Initial pairing waits are bounded, and rejected requests have a short cooldown. Discovery names and avatars alone are not authenticated. QR clients still require the complete original pairing secret and exact certificate pin; this alternative does not weaken QR authentication. Existing Windows clients keep using QR.

Control frames are UTF-8 JSON followed by LF, at most 65,536 bytes. No text reader may buffer past LF into a binary payload. File metadata: `id`, sanitized `name`, `size` (64-bit integer, 0 through 1 TB), `sha256`. A batch has 1–16 files with unique IDs. Paths, file URIs and local source filenames beyond the display name never travel in an offer.

Push: client sends `{v:1, op:"push", code, name, files:[...]}`. Receive host checks/approves, then responds `{ok:true, offsets:[...]}`. Pull: client sends `{v:1, op:"pull", code, name}` to a send host. After host approval, it responds `{ok:true, sender, files:[...]}`; the client receiver approves and responds with offsets.

The sender streams exactly `size-offset` raw bytes for each file in offer order. The receiver hashes the completed partial, publishes/renames only on a match, then sends `{ok:true,index:N}` before the next file. Errors use `{ok:false,error:"..."}` where a control response is expected. Socket EOF is an interrupted transfer, never completion. The sender waits for verification with a longer timeout. Resume offsets must be within 0..size; partials are keyed by expected hash and size. Repeated identical files in one batch resume only the first occurrence.

Android writes to pending MediaStore Downloads entries and clears `IS_PENDING` after successful verification. Windows stages in `.shareme-parts` and renames on success. Windows uses unique final filenames; Android relies on MediaStore's unique-name allocation. SHA256 is also checked for zero-length files. Receivers do not execute incoming files. Cancellation closes sockets and retains partials; signature verification and installation of APKs remain Android system actions.

The optional installer bootstrap is separate: a short-lived random local HTTP URL serves a small HTML page and the host's public Android APK. It cannot browse folders or serve user files. Regular transfer JSON and file payloads never use that HTTP channel.
